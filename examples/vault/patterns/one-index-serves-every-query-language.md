# 하나의 색인으로 여러 언어의 질의를 함께 처리하기

이 볼트는 언어별로 별도의 색인을 두지 않는다. 페이지 본문이 영어든 한국어든
같은 하나의 `.embeddings/` 저장소, 같은 하나의 임베딩 모델을 공유한다. 이게
가능한 이유는 밀집 검색(dense retrieval)에 쓰는 문장 임베딩 모델이 언어별로
분리된 벡터 공간이 아니라, 여러 언어의 의미를 같은 벡터 공간에 놓도록 학습된
다국어 모델이기 때문이다. 질의가 한국어이고 페이지 본문이 영어여도, 또는 그
반대여도, 두 텍스트의 벡터가 같은 공간에서 코사인 유사도로 비교된다 — 언어가
다르다는 사실 자체가 검색을 막는 장벽이 되지 않는다.

문제는 밀집 검색이 아니라 희소 검색(BM25) 쪽에 있다. BM25는 정확한 토큰 일치를
기반으로 하는데, 한국어는 교착어라서 어간에 조사가 그대로 붙어 나온다(예:
"질의를", "질의는", "질의가"). 공백으로 나눈 "단어" 단위로 토큰화하면 같은
어간이라도 조사가 다르면 전혀 다른 토큰이 되어버려서, 질의와 페이지가 같은
개념을 말해도 토큰이 하나도 겹치지 않는 경우가 흔하다. 이 코드베이스의
토큰화 함수는 이 문제를 한글 음절 바이그램(2글자씩 겹쳐 자르기)으로 보완한다
— 완전한 형태소 분석은 아니지만, 어간과 조사가 붙어 있어도 최소한 일부
바이그램은 공유되도록 만들어서 부분 일치를 가능하게 한다. 반대로 라틴 문자
토큰(API 이름, 필드명 같은 정확 매칭이 중요한 토큰)은 바이그램으로 쪼개지
않는다 — 쪼갤 경우 의미 없는 2글자 조각들이 늘어나 오히려 다른 페이지와의
우연한 토큰 충돌을 늘리기 때문이다.

언어학적으로 더 올바른 대안(형태소 분석기)도 실제로 시도되고 측정된 적이
있다. 2026-07-31 측정: 형태소 분석 토크나이저로 바꾸자 pattern 레이어의
Hit@3가 60.5%에서 50.0%로, 전체 Hit@3가 77.1%에서 73.9%로 떨어졌다 — 그래서
기본값으로 채택되지 않고 환경변수로 전환 가능한 대안으로만 남아 있다. 이
결과가 반직관적으로 보이는 이유는, 이 골드셋의 질의 다수가 정확히 같은
단어를 쓰지 않는 간접·개념적 질의라서, 형태소 분석의 정밀함보다 바이그램의
느슨한 부분 일치가 오히려 더 잘 맞아떨어지기 때문이다.

정리하면: 다국어 임베딩 모델이 밀집 신호를 언어 중립적으로 만들어 주고,
언어별 토큰화 보완(여기서는 한글 바이그램)이 희소 신호를 그 위에 맞춰 준다.
색인을 언어별로 나누지 않고도 교차언어 검색이 되는 것은 이 두 층이 각자의
역할을 하기 때문이다.
